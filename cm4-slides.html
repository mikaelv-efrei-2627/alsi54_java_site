1 Exceptions

Les exceptions permettent au développeur de traiter le “unhappy path” dans un programme.

1.1 Happy path

On écrit du code comme si tout se passait bien :

  • l’utilisateur n’entre pas de données erronées
  • le fichier à ouvrir existe
  • le disque n’est pas plein
  • la JVM a toujours de la mémoire
  • le réseau est disponible
  • …

1.2 Unhappy path

Le développeur doit décider comment le programme traite certains problèmes.

  • certains problèmes ne peuvent pas être traités. Ils doivent faire terminer le programme :
    • disque / mémoire pleins
    • bug
    • …
  • d’autres problèmes peuvent être traités.
    • saisie utilisateur erronée
    • réseau indisponible : réessayer
    • …

1.3 Lever une Exception

Une Exception est un objet Java qui peut être :

  • levé avec throw myException
  • attrapé avec try - catch
    public static double checkPositive(double nombre) {
        if (nombre < 0)
            throw new IllegalArgumentException("Le nombre doit être positif");

        return nombre;
    }
  • L’instruction throw stoppe l’exécution de la fonction et transmet l’exception à la méthode appelante.

1.4 Exception - appelant

Une méthode area qui appelle checkPositive a deux possibilités :

  1. ne rien faire => l’exception IllegalArgumentException est transmise à l’appelant de surface
    • si l’appelant est main, le programme se termine
    public static double area(double x, double y) {
        return checkPositive(x) * checkPositive(y);
    }

    public static void main(String[] args) {
        var s = surface(3, -2);
        // le programme se termine avec IllegalArgumentException
        System.out.println(s);
    }

1.5 Exception - try catch

  1. attraper l’exception avec try - catch
    public static double surfaceCatch(double x, double y) {
        try {
            return checkPositive(x) * checkPositive(y);
        } catch (IllegalArgumentException e) {
            e.printStackTrace(); // affiche la pile d'exécution
            return 0;
        }
    }

1.6 Exceptions - hiérarchie

1.7 Checked Exceptions

Si une “checked” exception est envoyée, la méthode qui l’entoure doit :

  • soit l’attraper avec try - catch
  • soit déclarer avec throws le ou les types d’exceptions pouvant être lancées
java.io.File
    public String getCanonicalPath() throws IOException {
        if (isInvalid()) {
            throw new IOException("Invalid file path");
        }
        return FS.canonicalize(FS.resolve(this));
    }

1.8 Checked Exceptions contamination

  • Une checked exception “contamine” toutes les méthodes appelantes.
  • Elles doivent toutes déclarer throws ..., jusqu’à ce que l’exception soit attrapée avec try - catch.
java.io.File
    public File getCanonicalFile() throws IOException {
        String canonPath = getCanonicalPath();
        // ...
    }

1.9 Unchecked Exceptions

  • Les exceptions “unchecked” n’ont pas besoin d’être déclarées dans les signatures de méthodes
  • Elles sont filles de l’une de ces 2 classes :
    • Error : en général ce sont des erreur impossibles à traiter
    • RuntimeException

1.10 try - catch - finally

  • Un bloc try - catch peut être suivi d’un bloc d’instructions finally
  • les instructions du bloc finally sont toujours exécutées, même si une exception est lancée
  • usage typique : fermer proprement une ressource
    public static int getPlayerScore(File file) {
        Scanner contents = null;
        try {
            contents = new Scanner(file);
            return Integer.parseInt(contents.nextLine());
        } catch (FileNotFoundException ex) {
            System.err.println("File not found: " + file);
            return 0;
        } finally {
            if (contents != null) {
                contents.close();
            }
        }
    }

1.11 try with resource

  • La syntaxe précédente est un peu verbeuse
  • si la ressource implémente AutoCloseable, la fermeture peut se faire automatiquement
java.lang.AutoCloseable
public interface AutoCloseable {
    void close() throws Exception;
}
  • il faut initialiser la ressource avec try(var ressource = new ...) { ... }
    public static int getPlayerScore(File file) {
        try (var contents = new Scanner(file)) {
            return Integer.parseInt(contents.nextLine());
        } catch (FileNotFoundException ex) {
            System.err.println("File not found: " + file);
            return 0;
        }
    }

1.12 try avec plusieurs catch

  • le bloc try peut envoyer plusieurs types d’exceptions
  • on peut décider de les traiter différemment
public static int getPlayerScore(File file) {
    try (var contents = new Scanner(file)) {
        return Integer.parseInt(contents.nextLine());
    } catch (IOException e) {
        System.err.println("Player file wouldn't load!", e);
        return 0;
    } catch (NumberFormatException e) {
        System.err.println("Player file was corrupted!", e);
        return 0;
    }
}

1.13 try avec union catch

  • Lorsque le même traitement s’applique à plusieurs types, on peut les “catch” avec Exception1 | Exception2 | ...
public static int getPlayerScore(File file) {
    try (Scanner contents = new Scanner(file)) {
        return Integer.parseInt(contents.nextLine());
    } catch (IOException | NumberFormatException e) {
        logger.warn("Failed to load score!", e);
        return 0;
    }
}

2 Exceptions : bonnes pratiques

2.1 Do not swallow

  • ne pas “avaler” les exceptions
public static int getPlayerScore(File file) {
    try (Scanner contents = new Scanner(file)) {
        return Integer.parseInt(contents.nextLine());
    } catch (Exception e) { }
    return 0;
}

Au lieu d’avaler l’exception, il vaut mieux :

  • soit lancer un nouveau type d’exception qui sera pris en charge par l’appelant
  • soit imprimer ou logger l’erreur

La fonction appelante ne sait pas pourquoi le fichier n’a pas été chargé.

2.2 Re-throw

public static int getPlayerScore(File file) throws GameException {
    try (var contents = new Scanner(file)) {
        return Integer.parseInt(contents.nextLine());
    } catch (Exception ex) {
        throw new GameException("Couldn't load the score", ex);
    }
}
public class GameException extends Exception {
    public GameException(String message, Throwable cause) {
        super(message, cause);
    }
}

2.3 Afficher l’exception

  • Alternativement, on peut afficher l’exception sur la console:
    public static int getPlayerScore(File file) throws GameException {
        try (var contents = new Scanner(file)) {
            return Integer.parseInt(contents.nextLine());
        } catch (Exception ex) {
            ex.printStackTrace();
            return 0;
        }
    }

2.4 Logger une exception

  • mais dans dans des projets importants, il est préférable d’utiliser un système de logging
    private static final Logger logger = Logger.getLogger(this.getClass().getName());

    public static int getPlayerScore(File file) throws GameException {
        try (var contents = new Scanner(file)) {
            return Integer.parseInt(contents.nextLine());
        } catch (Exception ex) {
            logger.log(Level.WARNING, "Couldn't load the score", ex);
            return 0;
        }
    }

2.5 finally : ne pas utiliser return

  • une autre façon d’avaler une exception est d’utiliser return dans le bloc finally
public static int getPlayerScore(String playerFile) {
    int score = 0;
    try {
        throw new IOException();
    } finally {
        return score; // <== IOException est perdue
    }
}

2.6 finally : ne pas utiliser throw

  • lorsqu’on lance une exception dans le bloc finally, l’exception originale est perdue.
public static int getPlayerScore(String playerFile) {
    try {
        // ...
    } catch ( IOException io ) {
        throw new IllegalStateException(io); // <== mangée par le finally
    } finally {
        throw new OtherException();
    }
}

2.7 checked vs unchecked

  • les “checked” exceptions sont à utiliser lorsque l’appelant peut raisonnablement traiter le problème.
  • cela force l’appelant à le faire, car la méthode déclare l’exception dans sa signature
  • si l’appelant ne peut rien faire, utiliser une “unchecked” exception qui hérite de RuntimeException
  • les développeurs d’un projet peuvent parfois décider de n’utiliser que des “unchecked”. C’est un débat passionné, voir The case against checked exceptions

3 Tests unitaires

En programmation, le test unitaire est une procédure permettant de vérifier le bon fonctionnement d’une partie précise d’un logiciel ou d’une portion d’un programme (appelée « unité » ou « module »).

3.1 Introduction

Les tests unitaires sont une étape cruciale dans l’implémentation d’un logiciel. Ils permettent de rendre le code :

  • plus robuste : les cas limites sont couverts
  • plus lisible : ils constituent une forme de documentation
  • plus maintenable : en cas de refactoring, ils permettent de vérifier que le programme fonctionne toujours

3.2 Introduction à JUnit

En Java, plusieurs outils permettent d’écrire des tests unitaires. Nous utiliserons JUnit, qui est le plus populaire.

Un test est une classe contenant des méthodes annotées @Test :

import org.junit.jupiter.api.Test;

import static org.junit.jupiter.api.Assertions.assertEquals;

public class CircleTest {

    @Test
    void testSurface() {
        double actual = new Cercle(1.0).surface();
        double expected = 3.141592653589793;
        assertEquals(expected, actual);
    }
    
    @Test
    void testScale() {
        // ...
    }
}

3.3 Conventions - classe

  • la classe de test est le nom de la classe à tester, suivie du suffixe Test.
  • elle est située dans le même package
  • elle est située dans un répertoire différent du code de production.

Cela évite toute possibilité d’exécuter du code de test en production.

3.4 Conventions - méthodes de test

  • Dans l’exemple précédent, testSurface ne nous dit pas beaucoup de choses sur ce qui est testé.
  • Une bonne pratique est d’utiliser la formulation “Given / When / Then” dans les noms des méthodes.
  • Vous pouvez aussi les ajouter en commentaires pour délimiter les blocs d’instructions correspondantes.
    @Test
    public void givenRayon1_whenSurface_thenReturnSurface() {
        // GIVEN
        var cercle = new Cercle(1.0);
        // WHEN
        double actual = cercle.surface();
        // THEN
        double expected = 3.141592653589793;
        assertEquals(expected, actual);  
    }

    @Test
    public void givenRayonDoubleMaxValue_whenSurface_thenReturnSurfaceInfinity() {
        //...
    }

3.5 Conventions - Given/When/Then

La formulation “Given / When / Then” permet d’écrire des tests d’acceptation, qui seront plus parlants pour discuter des spécifications avec un utilisateur final ou un chef de projet.

  • Given : bloc qui prépare les données. Quelles sont nos données d’entrée ?
  • When : action(s) effectuées, ou scénario de test. Ça sera typiquement un appel de méthode. Mais ça peut être une requête HTTP, …
  • Then : quelles sont les sorties ou conséquences de l’action ? Quelles assertions allons nous vérifier ?

3.6 Assertions

Junit fournit de nombreuses méthodes pour écrire les assertions.

  • assertEquals(expected, actual) compare 2 types primitifs ou 2 objets en utilisant .equals
  • assertThrows(expectedType, executable) vérifie qu’une instruction lance une exception spécifique
  • assertNull(obj) teste si un objet est null
  • assertTrue(expr) teste si une expression booléenne est true
  • voir Junit assertions

4 Tests unitaires : bonnes pratiques

4.1 Test Driven Development

Le TDD est une méthodologie très efficace. Elle a 3 règles simples :

  1. Vous n’êtes pas autorisé à écrire du code de production, sauf si c’est pour faire passer un test unitaire en échec.
  2. Vous n’êtes pas autorisé à écrire plus de code dans un test unitaire que ce qui est nécessaire pour le faire échouer ; et les erreurs de compilation sont considérées comme des échecs.
  3. Vous n’êtes pas autorisé à écrire plus de code de production que ce qui est nécessaire pour faire passer le test unitaire en échec.

Voir TheThreeRulesOfTdd

4.2 Écrire des tests spécifiques

Une méthode de test doit tester un seul scénario.

  • au lieu d’ajouter de nombreuses assertions au même test, créer d’autres tests.
  • ainsi, en cas de problème, il sera plus facile de déterminer quel scénario a échoué

4.3 Tester des cas réels

Les tests doivent refléter des cas réels d’utilisation du programme. Cela facilite la compréhension du code dans certains cas se produisant en production.

  • donner des vrais noms aux utilisateurs, personnes, …
  • utiliser des montants, taux d’intérêt, … réalistes
  • enchaîner une suite d’actions que l’utilisateur fait régulièrement

4.4 simuler (Mock) les services externes

  • Un logiciel va typiquement dépendre de services externes: API Web, base de données, fichier, …

  • Il est souhaitable de simuler (mock) ces services externes. On pourra utiliser des interfaces avec une implémentation de test, ou des frameworks comme Mockito

  • si les services externes ne sont pas simulés, les tests vont être lents et parfois imprévisibles

4.5 Éviter le copier / coller

  • les différents scénarios de tests sont souvent similaires
  • il est tentant de copier/coller et changer juste la préparation ou les assertions
  • comme pour le code de production, il est préférable de supprimer le code redondant en créant des fonctions utilitaires

4.6 Couverture 80 %

  • IntelliJ offre un outil de code coverage
  • cela permet de savoir si le code de notre projet est couvert par des tests
  • une couverture à 100% est difficile à obtenir

Une bon compromis est cibler 80% de couverture.

4.7 Automatiser avec CI / CD

Dans une équipe de développement, la suite de tests est exécutée automatiquement.

  • selon les équipes, cela peut être après chaque git push, ou seulement après un merge
  • cela permet d’interdire de livrer en production du code qui ne passe pas tous les tests

L’exécution de la suite de tests fait partie d’un pipeline “Continuous Integration” / Continuous Delivery.
