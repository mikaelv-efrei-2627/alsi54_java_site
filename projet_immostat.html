Projet Immostat

Author

Mikaël Valot

1 Introduction

Le projet Immostat vise à développer un outil d’analyse des données de mutations immobilières en France. Ces données, appelées “Demandes de Valeurs Foncières” (DVF), sont publiées par l’administration fiscale et mises à disposition du public sur le portail data.gouv.fr.

Le jeu de données DVF contient l’ensemble des transactions immobilières (mutations, échanges, donations) enregistrées depuis 2014. Pour chaque transaction, on dispose d’informations détaillées : localisation (commune, section cadastrale, parcelle), caractéristiques du bien (type, surface), prix de mutation, date de mutation, etc.

Ce projet vous permettra de mettre en pratique vos compétences en Java pour :

  • Parser et nettoyer des données réelles volumineuses
  • Concevoir un modèle de données adapté et une architecture logicielle robuste
  • Implémenter un système de stockage persistant (base de données)
  • Développer une interface en ligne de commande (CLI) ergonomique
  • Effectuer des analyses statistiques et des requêtes complexes
  • Générer des visualisations (cartes, graphiques)

2 Objectifs pédagogiques

Ce projet permet de travailler les compétences suivantes :

  • Conception orientée objet : modélisation de domaine, hiérarchie de classes, encapsulation
  • Gestion de données : parsing de fichiers, nettoyage de données, persistance en base de données
  • Architecture logicielle : séparation des responsabilités (DAO/Repository, Services, UI)
  • Développement itératif : construction progressive de fonctionnalités
  • Travail en équipe : collaboration via Git, répartition des tâches, code review
  • Utilisation de bibliothèques tierces : JLine, JDBC, Apache POI
  • Concevoir une Interface utilisateur : CLI avec autocomplétion et aide contextuelle

3 Déroulement du projet

  • 3 parties, une par séance
  • Groupes de 3 personnes
  • Projet itératif. Le code produit dans une séance servira de base à la prochaine séance.

Sessions :

  • séance 1 (3h30) : découverte, chargement de données, requêtes simples, calculs statistiques.
  • séance 2 (3h30) : partie 2 - ajout de nouvelles fonctionnalités
  • séance 3 (1h45) : partie 3 - ajout de nouvelles fonctionnalités

3.1 Déroulement d’une séance

  1. Lecture du cahier des charges, questions à l’enseignant
  2. Répartition des tâches (vous pouvez travailler en pair programming)
  3. Développement, tests, rédaction de la documentation
  4. Au cours de la séance, votre enseignant invitera votre groupe à un échange de 10-15 mn :
    • Il vous posera des questions de compréhension de votre code
    • Il répondra à vos questions et pourra vous donner des conseils
  5. Vous devrez soumettre votre travail (commit & push) avant la fin de la séance.
    • pas de travail en dehors des heures de classe, pas de rush pour finir à la dernière minute.
      • respect du principe eXtreme Programming Sustainable Pace
    • vous devez utiliser le temps disponible efficacement.
    • vous pouvez continuer à travailler sur le projet en dehors des heures de cours, mais ce travail ne sera pas noté
    • les commits contenant beaucoup de modifications seront considérés comme suspects : fait avec IA ?
      • committez souvent

7 Format des données

7.1 Fichier Geo-DVF

Le fichier geo-dvf_2025_01.sample.csv utilise le format Geo-DVF, une version enrichie et simplifiée des données DVF :

  • Format : CSV (délimiteur virgule ,)
  • Encodage : UTF-8
  • Première ligne : en-têtes de colonnes
  • Avantage : coordonnées GPS incluses, noms de communes inclus, format plus simple que le DVF brut

Documentation complète : Demandes de valeurs foncières géolocalisées

Colonnes clés pour le projet :

  • id_mutation : identifiant unique de la mutation (permet de regrouper les lignes d’une même vente)
  • date_mutation, nature_mutation, valeur_fonciere : caractéristiques de la transaction
  • code_commune, nom_commune, id_parcelle : localisation
  • type_local (Maison/Appartement/Dépendance), surface_reelle_bati, nombre_pieces_principales : caractéristiques du bien
  • surface_terrain, nature_culture : terrain
  • longitude, latitude : coordonnées GPS

Particularité importante : une même mutation occupe souvent plusieurs lignes (maison + dépendance + terrain). Ces lignes partagent le même id_mutation et doivent être regroupées.

Exemple : mutation “2025-1” = 3 lignes (jardin + maison + dépendance)

9 Première partie

9.1 Contexte

Dans le dossier data/, le repository contient un échantillon des données Geo-DVF pour le département de l’Ain.

Pour travailler sur des données complètes :

  • Téléchargez le fichier de votre département préféré depuis Données brutes Geo-DVF

9.2 Stockage en base de données

Vous devez utiliser H2 Database pour stocker les données de manière persistante. H2 est une base de données relationnelle embarquée, écrite en Java, qui ne nécessite aucune installation. La dépendance est déjà configurée dans le pom.xml.

Connexion JDBC :

String url = "jdbc:h2:./data/immostat";  // Crée immostat.mv.db dans data/
Connection conn = DriverManager.getConnection(url, "sa", "");

Schéma

  • Créez votre shema dans un fichier src/main/resources/schema.sql
  • Créez un script de destruction dans src/main/resources/drop-schema.sql contenant des DROP TABLE
  • Créez un script de nettoyage dans src/main/resources/clear-schema.sql contenant des TRUNCATE TABLE
  • Ouvrez ce fichier dans IntelliJ, et configurez la connection pour pouvoir l’exécuter.

Architecture recommandée :

  • Créer des tables SQL pour stocker les mutations et leurs caractéristiques
  • Utiliser le pattern DAO (Data Access Object) pour encapsuler les requêtes SQL
  • Penser à indexer les colonnes fréquemment utilisées dans les filtres (commune, date, type local)

9.3 Travail à réaliser

9.3.1 Conception du modèle de données

Modèle relationnel (schéma de base de données) :

  • Identifier les entités principales
  • Définir les relations entre elles (1-N, N-N)
  • Créer le schéma SQL avec les types appropriés
  • Prévoir les index pour optimiser les requêtes

Modèle objet (classes Java) :

  • Créer des classes correspondant aux entités
  • Utiliser des types appropriés (LocalDate, BigDecimal, enums…)
  • Implémenter equals/hashCode/toString si nécessaire

Point d’attention : une mutation peut concerner plusieurs biens (maison + dépendance, appartement + parking, etc.). Votre modèle doit refléter cette réalité.

9.3.2 Chargement des données

Implémenter la commande load <fichier> qui :

  • Parse le fichier DVF (format pipe-delimited)
  • Nettoie les données :
    • Regroupe les lignes concernant une même mutation (même identifiant de mutation)
    • Gère les valeurs manquantes ou aberrantes
    • Convertit les types (dates, nombres, etc.)
  • Stocke les données en base H2
  • affiche un résumé (nombre de lignes lues, mutations créées, erreurs)

Exemple d’utilisation :

immostat> load data/valeursfoncieres-2025-S1-sample.txt
✓ 50 lignes lues, 28 mutations enregistrées, 0 erreurs

9.3.3 Commandes d’analyse statistique

Implémenter les commandes suivantes :

a) count [filtres] : nombre de mutations

immostat> count
Total : 28 mutations

immostat> count commune=farges
Total pour commune=farges : 15 mutations

b) stats [filtres] : statistiques sur le prix au m²

immostat> stats type=maison
Prix au m² (maisons uniquement) :
  Moyenne   : 2 450 €/m²
  Minimum   : 1 200 €/m²
  Maximum   : 4 800 €/m²
  Écart-type: 850 €/m²
  Médiane   : 2 300 €/m²

9.3.4 Filtres de recherche

Toutes les commandes d’analyse doivent accepter des filtres optionnels :

Filtres géographiques :

  • commune=<nom> : limite à une commune (ex: FARGES)
  • section=<prefixe+section> : limite à une section cadastrale (ex: 000AB), (obtenue depuis id_parcelle)
  • rue=<nom> : limite à une rue (recherche textuelle partielle)

Filtres temporels :

  • annee=<YYYY> : année de mutation (ex: 2025)
  • trimestre=<YYYY-QN> : trimestre (ex: 2025-Q1)
  • mois=<YYYY-MM> : mois (ex: 2025-01)

Filtres sur le bien :

  • type=<maison|appartement|terrain|local> : type de bien

Exemples de combinaisons :

immostat> stats commune=01158 type=maison annee=2025
immostat> count rue="Victor Hugo" trimestre=2025-Q1

9.3.5 Interface en ligne de commande

L’application utilisera JLine pour créer une application CLI interactive avec :

  • Autocomplétion des commandes (help, load, count, stats, histogram, exit)
  • Autocomplétion des chemins de fichiers pour la commande load
  • Historique des commandes (flèches haut/bas)
  • Commande help affichant la liste des commandes disponibles
  • Gestion des erreurs avec messages clairs

10.4 Travail à réaliser

10.4.1 Commande evolution

Implémenter la commande evolution <fichier.xlsx> [filtres] qui génère un rapport d’évolution des prix :

immostat> evolution data/rapport_gex.xlsx commune=Gex periode=trimestre
✓ Rapport généré : data/rapport_gex.xlsx (12 périodes)

Contenu du fichier Excel :

Période Nb ventes Prix moyen Prix médian Prix/m² moyen Prix/m² médian
2024-T1 15 320 000 € 295 000 € 3 200 € 3 050 €
2024-T2 22 335 000 € 310 000 € 3 350 € 3 180 €
…

10.4.2 Spécifications

Calculs (en Java) :

  • Regrouper les mutations par période
  • Pour chaque période, calculer : nombre de ventes, prix moyen, prix médian, prix/m² moyen, prix/m² médian
  • Réutiliser la logique de calcul de la partie 1

Granularité temporelle :

  • Par défaut : trimestre
  • Option periode=mois : regroupement mensuel (2024-01, 2024-02, …)
  • Option periode=trimestre : regroupement trimestriel (2024-T1, 2024-T2, …)
  • Option periode=annee : regroupement annuel (2023, 2024, 2025)

Mise en forme Excel :

  • En-têtes avec style (gras, couleur de fond)
  • Format monétaire pour les colonnes de prix (#,##0 €)
  • Largeur de colonnes adaptée au contenu

Graphique :

  • Ajouter un graphique courbe montrant l’évolution du prix/m² médian
  • Le graphique peut être sur la même feuille ou sur une feuille séparée

10.4.3 Filtres

La commande accepte les mêmes filtres que les commandes de la partie 1 :

  • commune=<nom> : limite à une commune
  • type=<maison|appartement> : limite à un type de bien
  • periode=<mois|trimestre|annee> : granularité temporelle

Exemples :

immostat> evolution rapport.xlsx commune=Gex type=maison
immostat> evolution rapport.xlsx commune=Farges periode=mois

11.1 Architecture du code

Organisez votre code en packages logiques :

immostat/
├── model/           # Classes du domaine (Vente, Bien, etc.)
├── dao/             # Data Access Objects (accès BDD)
├── service/         # Logique métier (calculs stats, nettoyage)
├── cli/             # Interface en ligne de commande
├── parser/          # Parsing des fichiers DVF
└── Main.java        # Point d'entrée
  • Commencez par implémenter un chargement simple avec peu de colonnes
  • Une fois que vous avez un code de base qui fonctionne, ajoutez les tables/colonnes nécéssaires

11.2 Accès aux données

  • Réutilisez la classe DatabaseConnection du tp5
  • Passez là en paramètre du constructeur de vos dao.

11.3 Gestion des erreurs

  • Utilisez des exceptions spécifiques (pas juste Exception)
  • Loggez les erreurs (System.err ou SLF4J)
  • Affichez des messages clairs à l’utilisateur
  • Ne faites pas planter l’application sur une erreur non critique

11.4 Performance

  • Utilisez des requêtes SQL préparées (PreparedStatement)
  • Chargez les données par batch (transactions)
  • Fermez les ressources (try-with-resources)
  • Pour de gros fichiers, évitez de tout charger en mémoire

11.5 Git

  • Commitez régulièrement (au moins toutes les 30 min)
  • Messages de commit clairs et descriptifs
  • Créez une branche par fonctionnalité si nécessaire
  • N’oubliez pas de push avant la fin de la séance

11.6 Utilisation de l’IA

Vous pouvez utiliser l’IA pour :

  • poser des questions sur une API
  • vous aider à résoudre des erreurs de compilation
  • de la complétion de code simple (inline completion OK, github copilot NON)
  • générer du code SQL

Vous ne devez pas utiliser une IA pour générer le code Java du projet.

12.1 FAQ

Q: Dois-je gérer tous les types de mutations (échanges, donations, etc.) ? R: Non, concentrez-vous uniquement sur les mutations (Nature mutation = "Vente").

Q: Comment identifier qu’une maison et sa dépendance font partie de la même mutation ? R: Elles partagent le même identifiant de mutation (combinaison date + commune + n° de disposition).

Q: Que faire des mutations sans surface ou sans prix ? R: Vous pouvez les exclure des statistiques de prix/m² mais les compter quand même dans count.

Q: L’histogramme doit avoir combien de bins par défaut ? R: 10 bins est une bonne valeur par défaut. Permettez à l’utilisateur de le configurer avec --bins=N.

Q: Faut-il gérer les accents dans les noms de rues ? R: Oui, utilisez une recherche insensible à la casse et aux accents si possible.

Q: Pourquoi H2 ?

  • Fichier unique (.mv.db)
  • JDBC standard (comme PostgreSQL, MySQL, etc.)
  • Performante pour de gros volumes
  • Console web intégrée pour explorer les données
  • Zéro configuration
